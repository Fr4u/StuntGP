# Fixes for bugs in the original

User decision, 27 September 2026: bugs in the original are to be fixed while keeping its feel. The fixes must be described separately from recovered behaviour. This approval does not mean replacing the physics, controls or game rules with another model. The unchanged evidence is still in `evidence/retail` and `evidence/decomp`.

## PORT-FIX-001: uninitialised sound-zone vector

Function `4278A0` writes only the XYZ of the cross product of V and N, leaving the local W at `[EBP-18]` uninitialised. `44F050` and `44EE50` carry W into the translation component of the matrix. Instruction `427925 FADD [EBP-34]` uses it numerically. The result of the zone selection therefore depended on earlier stack contents, including internal system calls.

The fix sets **only the W of this local direction vector to +0.0**, before the matrix is built. The product of two directions remains a direction, and its homogeneous coordinate contributes no translation. This is a deliberate fix in the new implementation, not a claim that the original always had zero at this location.

All 168 x87 operations of the function are preserved, as are the order of roundings and writes, the six plane sign-bit tests, the zone data from the track, the persisted W of the V/N vectors, the zone selection order and the sound listener. The copies of the two private matrices reproduce the result of `44F050` and `44EE50`. This fix does not change forces, speeds, collisions, controls, the camera or the simulation step rate.

Basis: the pinned `StuntGP_D3D.exe`, SHA256 `4a1d234ce1f095a427bb7f2f0174294b8c85a8fdbbc29b62a3863156b2f16a1b`; ranges `4278A0..427B3F`, `44F050..44F0DB`, `44EE50..44EEAE`. Stack audit: `source-work/subagents/source-audio-region-stack-20260927`; mapping of the new code: `source-work/main/subagent-round14-20260927/AUDIO-REGION-TRANSLATION.json`.

Confirmation status: static analysis and compilation are separate from running the game. As the user decided, no tests and no game runs were performed. Fixing this bug does not mean that all race connections are complete.

## PORT-FIX-002: uninitialised W coordinate of the wheel positions

In function `414460` the local `[EBP-4]` receives no value before the read at `414538`. Four writes, `41453B`, `4145D2`, `414667` and `414706`, then copy this value into the W of the wheel positions. Analysis of the whole range `414460..41470D` shows one read of this local word and no initialisation.

NEW initialises only this word with +0.0 and keeps all four source writes. This does not mean that the original stack contained zero. The XYZ position calculations, their roundings, the wheel spacing, the radii, the rotation matrices, the suspension timers and the shared random number generator remain unchanged. This is not a general zeroing of unreconstructed data.

Basis: the same pinned EXE as PORT-FIX-001; package `source-vehicle-wheel-update-20260927`, manifest SHA256 `7cac927334969642cf8949c17c38f54ec7565af59d7fae6ed8929bf3e9bd3315`. Independent review: `source-work/main/subagent-round15-20260927/WHEELS-STATIC-REVIEW.json`. The confirmation status remains static and compile-only; the game and the tests were not run.


## PORT-FIX-003: the AI reads a rival that does not exist

The original `407A70` and `407B20` search the six physical slots, skipping the current vehicle and inactive vehicles. When there is no second active vehicle, they return NULL. The reads at `407538`, `407C78` and `407E21` later use this null pointer. This is a bug in the original, not a missing driving formula.

NEW adds three checks at `407538`, `407C78` and `407E08`. A missing rival goes to the existing epilogues `4077A8`, `407DC7` and `407F54` respectively. In this situation there is no manoeuvre relative to a rival. Earlier writes and counter changes remain. When a rival exists, the calculations and the order of operations remain source-faithful; no substitute vehicle and no new throttle or steering value is created.

## PORT-FIX-004: negative full period of the track index

Ranges `4053A3..4053AB` and `4288FF..428907` compute `count - (abs(index) % count)`. For a negative whole multiple of the number of points the result is `count`, which points past the end of the array. Later instructions treat it as a point index.

NEW replaces only such a result equal to `count` with 0, at `4053AD` and `428909`. That is the first point of the same closed track. The other division remainders, the interpolation, the point positions and the steering calculations are preserved. A point count of zero remains a data error; the fix does not create a substitute track.

Basis for PORT-FIX-003/004: the pinned EXE named in PORT-FIX-001; package `source-vehicle-driver-assist-20260927`, manifest SHA256 `48fe5e581571e6c52d6090ca4d8483abdc08c9b1032a98c7ff634952aabc9ce2`, complete PE ranges and `TRANSLATION.json`. Integrator review: `source-work/main/subagent-round16-20260927/CONTACT-STAGING.json`, `CONTACT-AI-ADAPTER-REVIEW.json` and `CONTACT-MANUAL-REVIEW.json`. The five changed places are explicitly marked `NEW repair` in the code. The user approved fixing proven bugs in the original. The assessment remains static and compile-only, without running the game or the tests; full playability of the race is not confirmed.

## PORT-FIX-005: uninitialised W in the dynamics contact rotation (40F760, 44F8E0)

`40F760` builds three local direction vectors (`EBP-10/-20/-30`) and writes only XYZ; their W words (`EBP-4/-14/-24`) have no producer, and `40F822 -> 44F050` copies all four words. The same applies to the W of the product matrix columns (`EBP-E4/-D4/-C4`). `44F8E0` at `44F9B4` copies the never-written `EBP-24` as W. NEW sets **only these W words to +0.0** (places `40F763`, `44F8E3`, marked `NEW repair`). All XYZ calculations, the order of x87 operations and the physical writes remain source-faithful; `44EF40` consumes only XYZ. Package: `source-work/subagents/source-vehicle-dynamics-40fc90-r17`.

## PORT-FIX-006: negative remainder in the demo vehicle draw (40DD30)

`40DD30` takes the remainder modulo 6 of the signed `42F1F0` (`40DD3D CDQ`, `40DD43 IDIV`), so it can get -5..-1, and `40DD58` then reads `[49BDA0 + r*7724]`, which are addresses outside the vehicle array (49467C, 48CF58, 485834, 47E110, 4769EC). NEW treats a negative remainder as "vehicle inactive" without a read; the random number stream and the number of iterations are unchanged. In the pinned image none of these words has the value 1, so the practical behaviour is the same. Package: `source-work/subagents/source-core-race-pause-results-demo-r17`.

## PORT-FIX-007: the 26th and later laps overwrite the track index (41DD11)

In time trial and challenge (100 laps) the lap index stops at 25, and `41DD11` writes the lap result at `2440+25*4 = 24A4`, which is the vehicle's `spline_index`. `41DEE2` later uses it as the starting segment of the projection onto the track, which can corrupt progress and lap detection. NEW keeps the result for index 25 in a local variable that both comparisons read from; the rest of the logic is unchanged. The same group: `41DEFA..41DF02` has the negative full period bug identical to PORT-FIX-004 and receives the same fix. Package: `source-work/subagents/source-vehicle-progression-41e210-r17`.

## PORT-FIX-008: dead W of the cockpit camera axis (404450, mode 6)

Camera mode 6 copies the W of the forward/up axis of body part 0 (`404E45->404E50`, `404EF1->404EFC`) into the dead local `EBP-18`. These words come from the never-written stack words `413932`/`413917` of the vehicle drawing. Mode 6 reaches `RET 404FAC` without reading this local. NEW does not interpret these bits; only when they are unknown does the dead W get +0.0. The camera position, target and rotation are unchanged. Package: `source-work/subagents/source-race-path-audit-r17`.

Note (not a fix of the original): the R17 engine package fixed a NEW bug — address `60F2B4` was mapped to `clock.game_mode`, but it is `clock.phase` (gate `40ED30`).

Confirmation status of PORT-FIX-005..008: static analysis and compilation; the game and the tests were not run.

## PORT-FIX-009: wraparound of the 32-bit game clock counter (434820/434840/442490)

`434820` returns only the low 32 bits of `QueryPerformanceCounter` (`43482A CALL [46E05C]`, `434830 MOV EAX,[EBP-8]`), and `434840` takes the low 32 bits of the frequency and divides by 60. The tick loop comparisons are unsigned (`442834/442836`, `442888/44288A`, `441F1F/441F21`, `441F55/441F57`, `445900/44592E`), and `441EC0` handles only the case where the scheduled counter wraps first. When the observed counter wraps first, no tick runs for 0.5 s, and then a resynchronisation follows (`4424B5..4424D7`). At a typical 10 MHz this happens about every 7 min 9.5 s.

NEW feeds the source clock a host counter counted from application start and rescaled to 6000 Hz. The source arithmetic remains unchanged (an increment of exactly 100, i.e. 60 ticks/s, the same 0.5 s resynchronisation and the same unsigned comparisons). The first wraparound happens after more than 8 days of continuous running. Code: `source_host_counter_win32.cpp`, marked `NEW repair`. Package: `source-work/subagents/host-pacing-r18`.

Note (NEW platform code, not a fix of the original): the pace of the application loop is now tied to the game clock. A loop pass is slowed down only when the clock has an overdue tick, and the wait happens on the swap chain's latency object. Operations performed once per pass (previous key state `45F210`, controls `40DAD0`, sound ramps `462280`, light phases `42DCF0`, loading-screen frame counting `445940`) therefore run at the original's pace regardless of the monitor refresh rate. The order and content of the source functions have not changed.

## PORT-FIX-010: unwritten stack words as the W of vehicle part axes (4138A0, 4139F0, 413B60)

The vehicle drawing reads four local stack words that the original never writes to: `413917` (`EBP-4`, only at the far level of detail; at the near level it is the proven `1` from `413DA7 MOV ESI,1`), `413932` (`EBP-14`), `413AE5` (`EBP-24`) and `44F09B` (`EBP-14`, Y axis of the lighting base). It writes them as the W of the direction rows of the body-part and wheel matrices (`+3C`, `+2C`) and of base `4D5B30`. The value therefore depended on random stack contents. The vehicle modules later read these rows as full vectors.

NEW sets **only these four words to +0.0**, i.e. the homogeneous W of a direction vector. All XYZ, rotations, normalisations, the order of writes and the value `1` at the near level of detail remain source-faithful. Code: `src/source_vehicle_draw_graph.cpp` (`SourceVehicleDrawKnownPrefix::transport`), marked `NEW repair (PORT-FIX-010)`. Status: static analysis and compilation, without running the game.

## PORT-FIX-011: never-written words of the original read as 0 (clipping and trail buffers)

Several places in the original read words that nothing wrote before: the screen clipping buffer `4255E0`, undefined words of the input polygon copied by `425830`, unwritten words of the local frame of the trail rings `41F2F0`, and unknown bytes of contact values copied into `4D5B30` (`44F050`). NEW previously tracked their origin at run time and stopped the game on a numeric read. As the user decided (no emulation layers in the game), NEW defines them once, at the point of creation, as 0 (for the W of directions this corresponds to +0.0, as in PORT-FIX-008/010). In runs that previously finished correctly the result is identical, because these values were not used numerically. Origin tracking remains available only in the diagnostic build (`SGN_SOURCE_PROVENANCE=1`). Package: `source-work/subagents/perf-transport-r19`.

## PORT-FIX-012: trail point behind the camera as a screen vertex (41E410 → 41EF90 → 432F60)

When `41E410` rejects a trail ring point (depth below the camera's near plane, i.e. behind the camera or right next to it), the ring slot keeps the raw world X, Y, Z written just before the projection. `41EF90` later uses them as screen X/Y and as RHW, and the clipping in `4255E0` checks only X/Y. `432F60` draws such a fan (type 6, flags `14h` = `DONOTCLIP|DONOTLIGHT`) with an RHW equal to the world Z, which is negative on many tracks. D3D7 drew it without clipping, as a random triangle. The D3D12 pipeline cannot draw a vertex with RHW ≤ 0, so NEW stopped the game with the error "polygon GPU requires positive reciprocal W". This happened most often after the finish: the camera switches to mode 10, so the light trails and particles of the player's car are drawn (`mounted()` hides them only in modes < 10), and the car passes the trackside camera.

NEW does not change the source stream: the captured commands and vertices remain bit for bit. Only in the D3D12 drawing of `432F60` fans (type 6, non-indexed, flags `14h`) is every triangle that touches a vertex with RHW ≤ 0 replaced with a zero-area triangle. The index count, draw merging and interpolation markers do not change. All other draws keep the hard requirement of a positive RHW, and the error message now reports the command, type, flags and the XYZRHW words of the vertex. Code: `src/polygon_d3d12.cpp`, marked `PORT-FIX-012`. Analysis package: `source-work/subagents/rhw-r21`. Status: static analysis and compilation, without running the game.

## PORT-FIX-013: race language not set after idling on the language page (4452E0 → 445F80 → 445D70)

On a fresh installation (no `language.cfg` and no `save\card00\setup.bin`) the settings language word `5DF5F0` has the value 0. `43C060` zeroes it (`43C0D1`), and `43D280` does not change it without the file. The Setup page (`45A630`) opens the language page in stage 1 (`45A6DF`, kind 29, `43E000` → `452C00`, page class 1Dh). With `5DF5F0 = 0`, function `452C00` calls `445AD0` (`XOR EAX,EAX; RET`) and writes 0 back (`452CF6`). The language is set only by the player's choice (`452D70`, write `452D7C`). Without a choice, `43F610` for class 1Dh (byte `43F690+1Bh` = 0, i.e. a jump to `43F633`, read from the pinned EXE) calls `440880(2)`, `43EF10(1,1)` and `43DD70` after more than 3600 idle ticks `5FF460`. `43EF10` closes the whole page stack including Setup, so stages 2–4, including the automatic save `457EC0` in mode 3, do not run. After 3600 of its own ticks (`45C15F`) the title page starts the demo `43B0E0` → `43A720`, which copies `5DF5F0` into `60D744` (`43A751..43A758`). All ordinary race starts do the same (`43A2C7`, `43A7A3`, `43A931`, `43AA7C`, `43AC2F`, `43AE21`, `43AF55`). On entering the race scene, `442030` calls `42E6E0` → `42D070` → `4452E0`. With `612BEC = 1`, instructions `4452E9..4452EF` write 0 to `4835E0` through `445F70`. Then `44206B` → `445F80` compares 0 with the language loaded at start-up (1: the initial value of `4835E0` in `.data`, loading at `44215C`) and jumps to `445D70` with `EBX = 0`.

With `EBX = 0`, function `445D70` skips all value columns (`445DD5 TEST EBX,EBX; JZ 445DF3`), so in this call nothing writes the 256-byte value buffer `[EBP-148h]`. Even so, `445E60` → `445F10` copies it into the text arena for every recognised key. `strlen` then reads random stack contents, bounded only by the name terminator in `[EBP-48h]`. The race texts become stack garbage, and `612944` takes 0. The original never renews the arena budget `4835DC`, so the budget can run out and produce empty handles (`445F33..445F39`). NEW stopped the game at this point with the error "game text input outside authored language domain".

Fix: in `4452E0`, a value of 0 in `60D744` (language not set) is not passed to `445F70`. `4835E0` therefore keeps its previous value. On a fresh installation that is 1, i.e. English, the same language the menu runs in: `43D12F..43D145` selects the first row of `languagePC.csv`, flag 1. `445F80` then sees equality and does not reload the texts. Any other value is written exactly as in the original. The track index read at `4452F4` after the language write and the script path formatting do not change. The `445D70` loader and its domain 1..7 remain unchanged. `5DF5F0` still has the value 0, so on the next start the language page waits for a choice again, as in the original. Code: `src/source_selected_script.cpp`, marked `NEW repair (PORT-FIX-013)`. Package: `source-work/subagents/language-idle-r28`. Status: static analysis and compilation, without running the game or the tests.

## PORT-FIX-014: unwritten track vertices in the first world frame (42E8D0 → 429880/429730 → 433F40)

The world frame marker `61C508` has the value 0 in the PE image. Its only write is `42E8BC` in `42E870`, and the only caller of `42E870` is `4425D0`. The marker therefore increases only after the race world has been drawn, always after the `429A40` projection. The store of transformed vertices `61C50C` (`0x78000` bytes, 15360 slots of 32 bytes) is allocated on every scene load by `42E430` (`42E437`) through `42E8D0`. `42E8D0` zeroes the whole allocation (`42E964..42E974`), including the WORD marker `+12` of every slot. `429730` and `429880` skip a track base vertex when this word equals `61C508` (`429784..42978A` and `4298DD..4298E3`, jumps to `42983F` and `429A0A`). They treat such a vertex as already computed in this frame: they do not transform it, do not write the marker and do not append it to the indexed list `61C520`, so `429A40` does not project it. In the first world frame of the process (`61C508 = 0`) every slot meets the condition, because the zero from `42E8D0` looks like the current frame's marker. The track base packets then point to slots with XYZRHW = 0. The packets of the clipped list `624400` have zero masks, so `427530` rejects them through `427520`. The packets of the inner list `624410` (list `42A090`), however, reach `433F40`, which copies X/Y from `+0/+4`, and Z and RHW from `+1C` (`4335EA..4335FD`). D3D7 drew degenerate triangles at the point (0,0) from this for one frame, so the bug was invisible. The D3D12 pipeline requires a positive RHW. NEW therefore stopped the frame at the start of the first race with the error "polygon GPU requires positive reciprocal W (command 9, type 4, flags 1C, vertex 0/4, XYZRHW 00000000 00000000 00000000 00000000)". With a single-material sky, command 9 is the first draw of list `624410`: prologue `432A90` (2 states), `24=160`, `23=8`, texture and sky draw, `432A90` after the sky (2 states), texture of list `624410`, draw. The same bug of the original returns after every wraparound of the 16-bit marker, i.e. every 65536 world frames, for slots that nothing has written since allocation. A new allocation while the marker equals 0 also triggers it.

Fix: for the current `61C50C` allocation, NEW keeps host metadata (these are not source writes). It records which slots `429880` or `429730` have written since the zeroing by `42E8D0`. The allocation identity comes from the bank and never repeats, so a new allocation starts without markers. A never-written slot is not treated as computed in this frame, even when its zero marker equals `61C508`. It goes through the ordinary source path: appending to `61C520`, writing the marker, the `42979A`/`4298F1` kernel, and then the `429A40` projection. For every slot written earlier, the marker test is identical to the original. The other frames, the order of the indexed list, the values and the roundings therefore remain unchanged. The source words and `61C508` itself are unchanged too, and with it the lighting phase `(62497C-1) & 61C508` in `42A320`. Only the frame in which the original would have sent vertices with XYZRHW = 0 changes: the track is now computed correctly in it. The GPU path of the track (gpu_world, NEW code) uses the same markers when choosing CPU overrides. An unwritten slot is therefore computed by the shader instead of passing zero words. Code: `src/source_world_track_vertices.cpp`, `src/gpu_world_submission.cpp`, `include/sgn/retail_world_polygon_frame.hpp`, marked `NEW repair (PORT-FIX-014)`. Profiler counter: `world.portfix014_unwritten_track_vertex`. Package: `source-work/subagents/world-zero-vertex-r30`. Status: static analysis and compilation, without running the game or the tests.

## PORT-FIX-015: read past the end of the 16-byte `fmt` chunk of a music file (45FFD0, 4600FC)

Opening a music track, `45FFD0` allocates memory for the `fmt ` chunk of the WAV file with the size `cksize & FFFFh` (`46008B..460093`, `operator new` at `464029`) and reads `cksize` bytes into it (`4600A6 mmioRead`). It then copies five fields into the global `WAVEFORMATEX` at `62E058`: four DWORDs (`4600DB..4600F7`) and finally a WORD from offset `+10h` (`4600FC MOV CX,[ECX+10h]`, write `460100` to `62E068`, i.e. `cbSize`). All 18 supplied `Sound\Music\Track*.wav` files have a `fmt ` chunk 16 bytes long (plain PCM). The allocation is therefore 16 bytes, and `4600FC` reads two heap bytes past its end. Nothing wrote them before; their value depended on the random contents of the heap block (`46786C`). This value goes only into the `cbSize` of the format of the music buffer created at `45FF57` (`CreateSoundBuffer`, descriptor `14h/E8h`, format pointer `62E058`). For `WAVE_FORMAT_PCM`, DirectSound ignores the `cbSize` field, so in the original the bug was inaudible. NEW rejected these unknown bytes with the exception "4600FC fmt tail: unresolved allocator branch…". The game then ended at the first music start.

Fix: when the allocation is exactly 16 bytes, NEW sets **only these two never-written bytes** to 0, i.e. the `cbSize` of a plain PCM format. A `fmt ` chunk at least 18 bytes long is read as in the original. The other format writes, the order of operations, the free at `460107`, the `wFormatTag == 1` check (`46010F`), the subsequent `mmioAscend`/`mmioSeek`/`mmioDescend` and all error branches remain unchanged. The music buffer parameters, volume, streaming and looping do not change. Code: `src/source_music_wave_open.cpp`, marked `NEW repair (PORT-FIX-015)`. Package: `source-work/subagents/audio-r36`. Status: compilation with `/W4 /WX` and runs of a private copy of the game (menu and demo). A capture of the process audio confirms the menu music (`Track12`) and race music (`Track8`) playing; the CTest tests were not run.

## Note R21 (a NEW bug, not a fix of the original): vehicle particle emitters

The game world's vehicle loop (`418922..41893B`, replay `41899D..4189B6`) called older `contact::effects` adapters, which stopped the game when dividing by a zero `surface_rolling` ("tire particle rolling divisor outside finite nonzero domain"). The original performs an ordinary IEEE division on the x87 here. The source translations from R17 (`src/source_vehicle_particles.cpp`: `416A80`, `415880`, `417CA0`, `416F30`, `417800`, `4173E0`) are now called through `VehicleParticleStage` (`src/source_native_vehicle_update.cpp`), in the original order. These translations reproduce the polarity of the x87 comparisons, unordered operands and division as the original does.

## Note audio-r36 (a NEW bug, not a fix of the original): music never started at all

The host configuration sets `GAMELOCATION = R:\SGP`. For all loose files the application core redirects this virtual directory to the local folder `data\retail`. The music binding (`install_source_music_windows`), however, created its own file platform without this redirection. `44B3B0` therefore looked for `R:\SGP\Sound\Music\TrackN.wav` on a non-existent drive and returned a size of 0. `45F8F0`, faithfully to the original, then ended without sound and without any message. Neither the menu music nor the race music played. Further ANSI calls with the same path (`_fullpath` `463F7B`, `GetDriveTypeA` `45FE17`, `GetDiskFreeSpaceA` `45FE45`, `mmioOpenA` `45FFD0`) also received the virtual path. The music binding now uses the same redirection as the core. `463F7B` receives the real file path in ANSI encoding (in 8.3 form if needed, so that it fits in 260 bytes). The order and arguments of the source calls have not changed. Code: `src/source_music_disk_installed.cpp`, `src/source_music_windows_runtime.cpp`, `include/sgn/source_boot_config.hpp`, marked `NEW HOST (audio-r36)`. Only this repair revealed PORT-FIX-015.
